SECTION 01
Executive Functional Determination
The chatbot is a governed orchestration layer, never a financial system of record.
The assistant may understand natural language, but the consequential parts of billing must be deterministic. Identity, permissions, customer/invoice/payment resolution, totals, balances, currency, risk classification, approvals, action execution and terminal state come from authoritative services. The model supplies language understanding, summarization and drafting within those boundaries.
Launch functional objective
Move a user from a billing question to a verified answer or valid next action without forcing navigation across multiple modules.
Permit useful preparation and preview of billing work while keeping issuance, reconciliation, external sends and other mutations inside canonical domain services.
Make every material boundary visible: tenant, legal entity, customer/record, currency, commercial plane, risk, approval and action state.
Degrade safely when the model, retrieval system, provider or a billing dependency is unavailable; core Zoiko Billing remains usable without the assistant.
Produce testable evidence that no conversational wording can bypass authorization, immutable financial history or maker-checker policy.
Five functional authority modes
[TABLE: 6 rows x 4 cols]
Mode | Permitted behavior | Mutation? | Required controls
M0 — Explain | Product/knowledge guidance from approved sources | No | Source control; no tenant data unless authenticated
M1 — Inspect | Search/read/explain authorized billing records | No | Tenant/entity scope; field permissions; source links
M2 — Prepare | Construct drafts, proposed matches, messages or action parameters | No canonical mutation beyond approved draft objects | Validation; object binding; no irreversible effect
M3 — Preview | Generate server-authoritative preview for a consequential action | No business-state commit | Risk/permission/approval decision; versioned preview token
M4 — Execute | Submit a confirmed, authorized action through canonical service | Yes, only where enabled | Explicit confirmation; approval; idempotency; audit; authoritative result

SECTION 04
System Functional Context and Trust Boundaries
All consequential data and actions cross deterministic service boundaries.
Functional request path
Authenticate and resolve principal/session.
Resolve tenant, commercial plane, legal entity and page-bound context.
Classify intent and required authority mode.
Run policy/RBAC/risk checks before tool access.
Retrieve approved knowledge or authoritative billing data.
Generate explanation, draft or action parameters.
Validate structured output server-side.
For material actions: generate authoritative preview, obtain confirmation/approval, execute idempotently.
Refresh authoritative result and render structured outcome.
Emit audit/telemetry/evaluation events with safe provenance.

[TABLE: 8 rows x 4 cols]

SECTION 05
Global Conversation and Action State Machine
The conversational shell must not obscure business-state transitions.
[TABLE: 13 rows x 3 cols]
State | Meaning | Permitted next states
READY | Authenticated assistant ready; no active consequential action | INSPECTING, PREPARING, ERROR_SAFE
INSPECTING | Read/search/knowledge operation in progress | READY, PREPARING, ERROR_SAFE
PREPARING | Draft/proposal inputs being assembled | PREVIEW_REQUIRED, READY, ERROR_SAFE
PREVIEW_REQUIRED | Server preview required or being generated | AWAITING_CONFIRMATION, AWAITING_APPROVAL, ERROR_SAFE
AWAITING_CONFIRMATION | Exact preview rendered and confirm available | EXECUTING, PREVIEW_EXPIRED, READY
AWAITING_APPROVAL | Separate approval required | AWAITING_CONFIRMATION, EXECUTING, REJECTED, EXPIRED
EXECUTING | Canonical service mutation submitted | PROCESSING_ASYNC, SUCCEEDED, FAILED_SAFE
PROCESSING_ASYNC | Authoritative terminal result pending | SUCCEEDED, FAILED_SAFE
SUCCEEDED | Terminal success with source record | READY
FAILED_SAFE | No unverified success claim; action status known or queryable | READY, PROCESSING_ASYNC
PREVIEW_EXPIRED | Preview invalid because time/state/context changed | PREVIEW_REQUIRED, READY
ERROR_SAFE | Read/draft failure with no unauthorized side effect | READY
[END TABLE]
Global mutation invariants
No M4 action without a server-generated action request and authoritative policy decision.
No consequential confirmation inferred from free-form assistant text; confirmation control/event must bind to preview digest.
Every protected mutation uses idempotency/replay protection.
If the client loses the response after submission, query action status before retrying.
No assistant action can weaken immutable invoice/ledger history; corrections create governed successor/compensating records.
The model never receives direct database credentials or unrestricted mutation capability.

Uncertain mutation response rule
If a network/client/model failure occurs after a material action may have been submitted, the system MUST NOT tell the user to repeat the action immediately. It must query the action/idempotency status using the correlation/action ID. Only when the server proves no action was accepted may the UI offer a fresh submission.

SECTION 31
Appendix B — Reference End-to-End Functional Flows
These examples are implementation/QA reference paths, not UI copy.
Flow B1 — “Create and issue an invoice for Acme”
Resolve authenticated tenant, legal entity and billing permission.
Search/resolve Acme; disambiguate if multiple customers.
Resolve commercial basis, currency and required invoice fields.
Collect line items and missing required data.
Create/update canonical invoice draft; display server totals.
Generate authoritative issue preview with seller/customer, currency, totals, dates, numbering, tax result and approval requirement.
Capture explicit confirmation and approval if applicable.
Issue through idempotent invoice service action.
Refresh canonical invoice state and show invoice number plus delivery state separately.
Write structured assistant-action audit linking preview, confirmation, idempotency and invoice event.
Flow B2 — “Why is invoice INV-1048 still outstanding?”
Resolve invoice inside authorized tenant/entity.
Retrieve invoice state, amount, payments, credits, refunds/adjustments, allocations and due date.
Use authoritative balance service to obtain amount due.
Explain components and any pending payment/provider state.
Cite/open related payment/allocation/invoice records.
Offer only valid next actions such as inspect payment, reconcile unmatched funds or draft reminder.
Flow B3 — “Refund the last payment”
Resolve customer/payment unambiguously.
Check payment settlement and authoritative refundable balance/provider capability.
Determine risk, permission and approval requirement.
Collect amount/reason if missing.
Generate refund preview bound to payment/version and expiry.
Capture confirmation and maker-checker approval where required.
Submit idempotently.
Show requested/processing state until terminal provider/domain event.
Return final refund state and audit reference; never claim completion from acceptance alone.
