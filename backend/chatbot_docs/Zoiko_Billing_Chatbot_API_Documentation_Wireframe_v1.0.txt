Executive API Doctrine
Zoiko Billing should operate a contract-first chatbot integration model. The API layer exists to make AI actions explicit, constrained, observable and testable. The model may interpret intent and prepare structured requests; authoritative services determine permissions, business validity, financial state and mutation success.
[TABLE: 10 rows x 2 cols]
Doctrine | Non-negotiable API consequence
Authoritative state | No model response may be treated as financial truth without authoritative service data.
Tenant isolation | Tenant and legal-entity context are validated server-side; client-provided context is never blindly trusted.
Progressive authority | Explain/Inspect/Prepare/Preview/Execute are distinct capabilities and must be expressible in API scopes and response states.
Preview before consequence | Material mutations expose deterministic preview artefacts before execution when the FRS requires confirmation or approval.
Idempotent money movement | Retrying a financial mutation must not duplicate the economic effect.
Immutable history | Issued invoices and posted financial records are corrected through governed mechanisms, not destructive overwrite.
Evidence by default | Every consequential action returns correlation/audit identifiers sufficient for support, QA and forensic review.
Fail closed | Ambiguous identity, scope, entity, currency, permission, approval or financial state blocks mutation.
Two commercial planes | Tenant billing and Zoiko Billing SaaS subscription billing use explicit namespaces and authorization boundaries.
[END TABLE]

4. Global API Design Rules
[TABLE: 16 rows x 2 cols]
Rule ID | Rule
API-RULE-001 | Resource names use plural nouns; action endpoints are reserved for genuine commands that cannot be represented as safe resource state transitions.
API-RULE-002 | Every operation has a globally unique, stable operationId.
API-RULE-003 | Every mutation defines idempotency, concurrency and retry semantics.
API-RULE-004 | Every request is associated with authenticated subject, tenant, entity context and correlation ID.
API-RULE-005 | Server authorization is authoritative; UI hiding is never a security control.
API-RULE-006 | Money uses decimal strings or integer minor units as explicitly defined by schema; never binary floating point.
API-RULE-007 | Currency uses ISO 4217 codes and is never inferred when the economic meaning would change.
API-RULE-008 | Timestamps are ISO 8601/RFC 3339 with explicit offset/UTC; local business date is separately modeled where required.
API-RULE-009 | Stable enumerations are documented; unknown/new values must not crash tolerant clients.
API-RULE-010 | Responses never include secrets, payment card sensitive authentication data, model hidden reasoning, internal credentials or raw infrastructure diagnostics.
API-RULE-011 | Errors are machine-readable, human-readable and mapped to a recoverability class.
API-RULE-012 | List endpoints use deterministic pagination and documented filter/sort semantics.
API-RULE-013 | Destructive DELETE is not used for posted/issued financial records.
API-RULE-014 | Financial state returned to the model includes provenance and as-of semantics sufficient to avoid stale-state assertions.
API-RULE-015 | Two-plane separation is represented in path, scope, service and audit context; no implicit crossover.
[END TABLE]

7.3 Error safety
Never return stack traces, SQL fragments, credentials, internal hostnames, raw model prompts, policy secrets or unnecessary PII.
For ambiguous financial outcomes, return an explicit UNKNOWN/PENDING state plus a reconciliation/status endpoint; never transform transport uncertainty into success/failure by inference.
The chatbot must use code/recovery fields to decide whether to retry, ask for confirmation, refresh state, escalate, or stop.
8. Idempotency, Concurrency & Retries
[TABLE: 8 rows x 2 cols]
Concern | Contract requirement
Idempotency key | Required for invoice issue, payment allocation, reconciliation commit, credit posting, refund execution and any externally visible financial mutation.
Retention | Server documents how long an idempotency key is remembered; repeated identical requests return the original result/reference.
Payload mismatch | Same key with materially different request must return conflict and must not execute.
Concurrency | Mutable drafts and approval resources expose a version/ETag; stale writes fail.
Retry policy | GET/HEAD safe to retry; mutation retry allowed only under idempotency contract.
Timeout ambiguity | Client queries operation/status using correlation/action ID rather than blindly repeating.
Distributed sagas | Long-running financial workflows expose state transitions and compensation/exception handling, not hidden synchronous assumptions.
[END TABLE]
9. Pagination, Filtering, Sorting & Search
[TABLE: 8 rows x 2 cols]
Area | Required design
Pagination | Cursor-based preferred for high-volume mutable financial lists; page/offset only if authoritative service guarantees stable semantics.
Default/max page size | Explicit per endpoint; server caps requests.
Filters | Typed, documented and allow-listed. Never accept raw SQL-like filter expressions.
Date ranges | Explicit timezone/business-date semantics; inclusive/exclusive boundaries documented.
Sort | Allow-listed fields and deterministic tiebreaker.
Search | Full-text/customer/invoice number search is distinct from exact ID lookup; result confidence not treated as identity proof.
Totals | Expensive aggregate totals are opt-in or separate endpoints if required for performance.
[END TABLE]

11.2 Preview binding
Preview returns a deterministic preview_id/hash, resource versions, totals/currency, affected entity, warnings, approvals required and expiration timestamp.
Execution must reject expired or stale preview, changed authoritative resource version, changed entity, changed financial total or revoked permission.
Confirmation text shown to the user is generated from structured preview data; the model may explain it but may not substitute a different economic meaning.

13.2 Invoice state invariants
Issued invoice content is immutable except via explicitly modeled legally/commercially valid adjustment pathways.
Issue endpoint must recompute/validate totals server-side; it must not trust totals supplied by the model/client.

Successful issue returns invoice_id, number, status, issued_at, total, currency, evidence envelope and communication state separately.

Appendix D — Standards Notes
At the time this wireframe was prepared, the OpenAPI Initiative publishes OpenAPI Specification 3.2.0, dated 19 September 2025. Postman documentation describes migration from collection v2.1 JSON to a v3 YAML format and provides linting for the v3 collection format. Swagger UI remains an interactive documentation surface generated from an OpenAPI description. Engineering must nevertheless pin versions to the actually supported toolchain rather than assume every tool supports every current specification feature.
Final Engineering Doctrine

The API is the control boundary A sophisticated conversational experience is valuable only if the underlying contract is deterministic. Zoiko Billing’s chatbot may interpret, explain and orchestrate; the API layer must establish identity, authority, economic meaning, exact amounts, current state, approvals, idempotency and evidence before any consequential financial change occurs.
