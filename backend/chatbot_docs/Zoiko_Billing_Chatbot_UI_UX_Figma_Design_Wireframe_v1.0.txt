1. Executive Summary
This document defines the complete Figma and UI/UX design specification for the Zoiko Billing Chatbot. It translates the approved product, functional, API, data and knowledge requirements into a coherent visual system that designers can build in Figma and engineers can implement without inventing behavior during development.
The target experience is a governed billing assistant embedded in Zoiko Billing. It must support low-risk explanation and inspection with conversational speed while progressively introducing structure, previews, approvals and explicit confirmation as financial consequence increases.
1.1 Design outcomes
A native Zoiko Billing assistant experience rather than a generic floating chatbot pasted onto the product.
Fast answerability for billing questions, with concise evidence and financial-state provenance.
Clear progressive authority: Explain → Inspect → Prepare → Preview → Execute.
No dark patterns, accidental execution, hidden tenant/entity context or ambiguous money values.
Consistent desktop, tablet and mobile behavior using a shared component library.
A Figma source of truth that maps cleanly to engineering design tokens and production components.
WCAG 2.2 AA behavior designed into every interactive state, not added after handoff.
1.2 Product experience principle
[TABLE: 1 rows x 1 cols]
THE INTERFACE MUST SHOW WHAT CHANGED When the assistant moves from answering to proposing or committing a billing change, the UI must visibly change mode. The user must be able to distinguish a suggestion, a prepared draft, an authoritative preview, a pending approval and a completed operation at a glance.
[END TABLE]
1.3 Non-goals
Do not redesign the entire Zoiko Billing application.
Do not create a visually independent AI brand inside Zoiko Billing.
Do not use chat text alone for complex financial action review.
Do not allow the model to choose colors, icons or labels dynamically for risk-critical states.
Do not encode financial state only by color.
Do not make knowledge citations or audit references optional for grounded financial/compliance answers.

6.1 Component property doctrine
Prefer explicit Figma component properties to duplicate components.
Risk and state are separate properties; e.g., Risk=High and State=Expired.
Content length must be tested with realistic long customer names, invoice IDs and translated labels.
No component may rely on hidden layers for production-critical accessibility information.
Detached components are prohibited on Handoff pages unless justified and annotated.

7.1 Answer structure
[TABLE: 8 rows x 3 cols]
Answer type | Visual pattern | Required content
Simple product answer | Assistant message + optional citation | Direct answer; relevant navigation/action link.
Grounded policy answer | Message + citation cluster | Answer; policy name; effective/current context; sources.
Financial inspection | Summary card + supporting narrative | Amount/status; currency; entity; timestamp/provenance.
Ambiguous request | Clarification prompt | One decisive missing input at a time where possible.
Insufficient evidence | Abstention card | What is unknown; why; safe next step.
Permission denial | Access state | What cannot be accessed; safe navigation or admin path.
Degraded service | Degraded banner + bounded response | What is unavailable; which information remains reliable.

7.2 Streaming behavior
Stream explanatory text only when it improves perceived speed; do not stream action parameters into a preview as if they were authoritative.
Structured financial cards render after required fields validate.
Show “Checking…” or “Validating…” status while authoritative tools are running rather than fake typing indicators.
Allow user to stop generation without cancelling already-submitted financial operations; those operations require their own control/state.

Restricted source | Never reveal title/snippet beyond entitlement; display generic restriction message if necessary.
Superseded source | Never used normally; historical mode must be explicit and visually labeled.

8. Governed Financial Action UX
Figure 2. High-consequence action pattern: Preview → Confirm → authoritative receipt.
8.1 Mode transition
[TABLE: 7 rows x 3 cols]
Mode | UI treatment | What user may believe
Explain | Conversational answer | No financial change is being prepared or made.
Inspect | Read-only financial/resource cards | Data is authoritative as of shown context/time.
Prepare | Editable structured draft card | A proposal exists; nothing has been committed.
Preview | Authoritative preview + impact + expiry | System has validated what would happen if committed.
Execute | Explicit confirmation, approval or submit control | A governed operation is being requested/processed.
Receipt | Operation result with authoritative status | Only “succeeded/final” when API confirms finality.
[END TABLE]
8.2 Preview card anatomy
1. Action label using human language, e.g., “Issue invoice” or “Refund payment.”
2. Risk level expressed through copy/iconography, not merely color.
3. Affected customer/account/resource and immutable reference.
4. Legal entity and tenant/workspace context.
5. Money values with ISO currency and exact visible amount.
6. Fields that will change, showing before/after where applicable.
7. Side effects: communication, ledger entry, reconciliation impact, external processor interaction.
8. Approval requirement and approver role where known.
9. Preview generated timestamp and expiry/invalidation condition.
10. Primary “Continue/Confirm” and secondary “Edit/Cancel” actions with clear labels.
8.3 Explicit confirmation
[TABLE: 1 rows x 1 cols]
NO GENERIC “YES” FOR HIGH-RISK ACTIONS High-risk confirmation must restate the action and material value. Use controls such as “Confirm $2,480.00 USD refund” or a review screen with a single unambiguous submit action. Conversational “yes” may only be accepted where the FRS explicitly allows it and the active preview context remains valid.
[END TABLE]
8.4 State invalidation
[TABLE: 7 rows x 2 cols]
Change | Required UI response
Tenant/entity changes | Invalidate preview; explain context change.
Material amount/recipient changes | Return to Prepare/Preview; require fresh validation.
Underlying resource version changes | Show conflict; refresh authoritative preview.
Approval policy changes | Update required approval path; block outdated submit.
Preview expires | Mark Expired; disable confirm; offer Refresh preview.
Permission revoked | Block execution; preserve safe read-only context where permitted.
[END TABLE]
9. Core Task Flow Wireframes
9.1 Ask about billing
1. User asks a product, policy or billing-process question.
2. Assistant determines whether answer requires knowledge retrieval, financial inspection or both.
3. Relevant permitted sources are retrieved.
4. Assistant answers directly, showing citations when grounded content is material.
5. If answer implies an action, show a separate suggested action control; do not silently transition into execution.
9.2 Inspect invoices / balances
1. Resolve tenant/entity context.
2. Collect missing filters only if required.
3. Show read-only summary with result count, amount, currency, status scope and “as of” context.
4. Allow expandable list/table; preserve sort/filter semantics.
5. Resource row opens authoritative invoice/customer record.
6. Offer follow-up action such as Prepare reminder, but keep it visually distinct from inspection.
9.3 Prepare and issue invoice
1. Collect/resolve customer, seller entity, currency, commercial basis and line items.
2. Render editable structured draft; validate required fields inline.
3. User selects Review invoice.
4. API generates authoritative preview with totals, taxes/adjustments where applicable and recipient impact.
5. UI shows approval requirement if applicable.
6. Explicit confirmation submits issue request.
7. Receipt displays processing/final status and invoice reference only from authoritative API.
9.4 Payment allocation / reconciliation
1. Display unmatched payment and candidate invoices in a structured comparison pattern, not prose alone.
2. Show confidence/reasoning as decision support, never as authority.
3. User selects proposed match or modifies allocation.
4. Preview shows exact allocation amounts and any remainder.
5. Confirm/approval commits governed reconciliation operation.
6. Receipt links to payment, invoice(s), reconciliation and audit reference.
9.5 Refund
1. User invokes refund from a payment context or conversation.
2. Assistant reads refund eligibility and processor/state constraints.
3. Prepare screen captures reason and permitted amount.
4. Authoritative preview shows refund amount/currency, original payment, destination constraints, fees/side effects if applicable, and approval requirement.
5. Explicit confirmation submits request.
6. Receipt may be Pending/Processing; never imply settled funds until confirmed.
9.6 Report/export
1. Collect report scope, date range, entities, currencies and grouping.
2. Preview report criteria and estimated data scope.
3. For sensitive/exportable data, show access and data-egress warning when policy requires.
4. Generate asynchronously when needed and show progress.
5. Completion state provides controlled download link and expiry information.

14. UX Writing & Microcopy Standard
[TABLE: 10 rows x 2 cols]
Rule | Example
Use verbs that describe consequence | “Issue invoice” instead of “Continue” when the action commits issuance.
State finality precisely | “Submitted for approval” not “Done” when approval is pending.
Prefer canonical financial nouns | Invoice, payment, allocation, reconciliation, credit, refund.
Avoid anthropomorphic authority | “I checked the invoice service” is weaker than “Invoice status: Paid — as of …”.
Explain blockers concretely | “This preview expired because the invoice changed. Refresh to review the current total.”
Use concise source language | “Sources (2)” or named policy/resource links.
No false certainty | Use bounded uncertainty when evidence or service status is incomplete.
Do not blame users | Describe the condition and recovery path.
Keep destructive labels explicit | “Cancel refund request” rather than “Cancel” where ambiguity exists.
[END TABLE]

[TABLE: 1 rows x 1 cols]
FORMULA [Verb] + [material object/value] + [optional recipient/context]. Example: “Confirm $2,480.00 USD refund” or “Issue invoice INV-DRAFT-8821 to Northstar Labs”.

29. Final Design Doctrine
[TABLE: 1 rows x 1 cols]
LOCKED PRINCIPLE Zoiko Billing’s assistant must make complex billing easier without making financial consequence invisible. Conversation provides speed; structured UI provides control. Every material action must reveal context, amount, affected resource, authority, approval state and finality before the user can reasonably believe the operation is complete.
