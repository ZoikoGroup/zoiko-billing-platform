1.1 Purpose
This document defines the target technical architecture and the minimum engineering evidence required to operate the Zoiko Billing Chatbot safely in production. It bridges the product/functional specifications and the deployable implementation. It is intentionally implementation-oriented but does not replace source-code design documents, infrastructure-as-code, runbooks, DDL migrations or API specifications.

2. Architecture Principles & Non-Negotiable Invariants
[TABLE: 13 rows x 3 cols]
ID | Invariant | Architecture requirement
P-01 | Authoritative financial truth | Invoices, payments, balances, reconciliation, credits, refunds and commercial-account state remain owned by Zoiko Billing domain services/ledgers.
P-02 | Model has no inherent authority | An LLM may interpret intent and propose parameters, but cannot authorize itself, bypass policy or write directly to financial stores.
P-03 | Context before data | Every data-bearing request resolves user, tenant, legal entity, billing plane and effective permissions before retrieval or action.
P-04 | Preview before consequence | High-risk actions require deterministic authoritative preview, freshness/version validation and explicit confirmation; maker-checker applies when policy requires.
P-05 | Evidence by construction | Messages, retrieval provenance, action stages, approvals, tool calls, service responses and audit events share correlation IDs sufficient for reconstruction.
P-06 | Fail closed | Ambiguous identity, stale previews, unavailable authority services, missing policy or unresolved financial state must block or safely degrade rather than guess.
P-07 | Two-plane separation | Tenant billing and Zoiko Billing's own SaaS commercial billing are separate data/permission planes with no implicit crossover.
P-08 | Least privilege | Every user, service, worker and provider integration receives only the minimum permissions and network/data access required.
P-09 | Regional/data governance | Data placement, retention and provider routing respect tenant home-region, classification and jurisdiction policy.
P-10 | Replaceable AI provider | Core billing workflows do not depend on proprietary model behavior. The model gateway normalizes provider access and preserves policy independence.
P-11 | Asynchronous truth | Long-running actions expose durable job/state machines. Transport timeout never becomes inferred financial success or failure.
P-12 | Observable and operable | Every critical path has measurable SLIs, actionable alerts, kill switches, runbooks and rollback/recovery mechanisms.
[END TABLE]
2.1 Forbidden architecture shortcuts
Direct LLM-to-database or LLM-to-payment-provider credentials.
Chatbot-owned replicated financial ledgers used as authoritative state.
Client-supplied tenant/entity/role claims accepted without server resolution.
Model-generated SQL against production financial stores.
Unbounded agent loops or dynamic tool discovery in production financial workflows.
Shared vector namespace across tenants without hard authorization filters.
Logging raw secrets, payment credentials, unrestricted prompts or unnecessary PII.
Financial execution endpoints that lack idempotency, audit correlation or version/freshness controls.
3. Quality Attributes & Architecture Drivers
[TABLE: 11 rows x 3 cols]

8. Governed Financial Action Architecture
Figure 3 — Consequential financial action sequence
8.1 Action states
[TABLE: 11 rows x 3 cols]
State | Meaning | Permitted transition
DRAFT | Interpreted candidate parameters; no financial effect. | VALIDATING / CANCELLED
VALIDATING | Server resolves entities, permissions and business-rule prerequisites. | PREVIEW_READY / DENIED / FAILED
PREVIEW_READY | Authoritative calculated effect bound to versions/hash and expiry. | CONFIRMED / EXPIRED / SUPERSEDED / CANCELLED
CONFIRMED | User explicitly accepted exact preview. | AWAITING_APPROVAL / EXECUTING / EXPIRED
AWAITING_APPROVAL | Maker-checker or policy decision required. | APPROVED / REJECTED / EXPIRED
APPROVED | Required approval satisfied. | EXECUTING / EXPIRED
EXECUTING | Idempotent authoritative write in progress. | SUCCEEDED / PENDING / FAILED_UNKNOWN
PENDING | Durable async operation awaiting terminal event/status. | SUCCEEDED / FAILED
SUCCEEDED | Authoritative receipt confirms effect. | Terminal
FAILED / FAILED_UNKNOWN | Known failure or ambiguous external outcome. | RECOVERY / RECONCILIATION / Terminal per policy
[END TABLE]
8.2 Hard technical controls
Action execution API requires an action_id, valid preview_id/hash, confirmation evidence, approval evidence where required, actor/context snapshot and idempotency key.
Preview payload is generated from authoritative Billing services, not model arithmetic.
Resource versions/ETags are rechecked immediately before write; stale effects return conflict and require a new preview.
The executing service re-evaluates authorization even if upstream already authorized.
All terminal/pending results return a receipt or durable operation identifier and correlation ID.
The model never stores or receives raw PSP secrets, card credentials, banking passwords or service administrator credentials.
9. Model Gateway & AI Runtime Architecture
9.1 Model gateway responsibilities
[TABLE: 10 rows x 2 cols]
Capability | Requirement
Provider abstraction | Expose canonical chat/structured-output/embedding interfaces independent of any single model vendor.
Model registry | Approved model IDs, capabilities, max context, risk classification, region, cost and lifecycle status.
Routing | Route by task, data classification, latency/cost budget, region and availability; never solely by model preference.

Data minimization | Send only necessary context; redact/mask restricted fields before provider call when policy requires.
Timeout/budget | Per-call timeout, max tokens, max cost and step budget.

Safety telemetry | Record provider/model/prompt versions, latency, token count, policy outcome and safe error code; do not retain hidden chain-of-thought.
[END TABLE]
9.2 Model isolation
[TABLE: 1 rows x 1 cols]
No financial credentials in model context The model gateway receives user-visible financial facts needed for the task and opaque resource references where possible. It never receives privileged database credentials, PSP secrets, signing keys or unconstrained service tokens.
[END TABLE]
9.3 Prompt/runtime policy boundary
System prompts are policy-controlled configuration, not the sole security boundary.
All model-proposed actions are parsed into typed canonical objects and validated by deterministic services.
Tool list is compiled from effective capabilities; unavailable/unauthorized tools are not exposed to the model.
External/tenant documents are treated as untrusted content, never as higher-priority instructions.
10. Retrieval-Augmented Generation Architecture
10.1 Retrieval pipeline
[TABLE: 9 rows x 2 cols]
Stage | Architecture behavior
Namespace resolution | Resolve global/internal/jurisdiction/tenant/entity namespace set from authenticated context and task.
Query formulation | Generate bounded search query; preserve critical billing terms, IDs, jurisdiction and product version.
Lexical + vector retrieval | Hybrid retrieval over approved published chunks; authorization filters applied before/within search, not after answer generation.
Metadata filtering | Enforce status=published, freshness, classification, product, jurisdiction, tenant and entity constraints.
Reranking | Rerank only already-authorized candidates; authority/freshness can override semantic similarity.
Evidence set | Return source IDs, document/chunk versions, authority level, effective dates and excerpt hashes.
Answerability | If evidence is contradictory, stale or insufficient, return a controlled abstention/clarification state.
Citation assembly | Response cites retrievable evidence references; historical answers remain reconstructable via stored versions.
[END TABLE]
10.2 Index architecture
Vector and lexical indexes may be separate physical services or one platform, but authorization semantics must be identical.
Tenant content is physically or logically partitioned with hard tenant filters; cache keys include namespace/tenant and classification.
Embedding text is treated as derived sensitive data and inherits source classification/retention.
Deletion/retirement propagates to retrieval availability while historical evidence records preserve the prior citation reference as required.
10.3 Prompt injection boundary
[TABLE: 1 rows x 1 cols]
Retrieved content is data, not instruction Instructions inside customer documents, imported PDFs, emails or web-derived material cannot alter system policies, tool permissions, model gateway configuration or action-control requirements. Retrieval output is wrapped and labeled as untrusted evidence.
[END TABLE]

11.1 Data access pattern
[TABLE: 1 rows x 1 cols]
API-only financial access Chatbot services must access Zoiko Billing financial state through versioned domain APIs/events. Direct SQL access to Billing production ledgers is prohibited except separately governed operational tooling outside the chatbot runtime.
[END TABLE]
11.2 Data consistency model
Action chain and approvals require strong transactional consistency inside the chatbot evidence store.
Knowledge index is eventually consistent with published KB state but publication/revocation events must be observable and bounded.
Billing financial state uses the consistency semantics of authoritative domain services; chatbot snapshots are provenance evidence, never current truth after their as_of/version point.
Caches are disposable and must not be used to bypass revalidation for financial mutation.
12. Event-Driven & Asynchronous Architecture
12.1 Canonical event envelope
[TABLE: 1 rows x 1 cols]
event_id: uuid event_type: zb.chatbot.<domain>.<verb>.v1 occurred_at: RFC3339 timestamp correlation_id: uuid/string causation_id: uuid/string tenant_id: uuid | null legal_entity_id: uuid | null billing_plane: TENANT | ZOIKO_COMMERCIAL subject: {type, id, version} actor: {type, id} schema_version: 1 payload: {...redacted/typed...}
[END TABLE]
12.2 Event principles
At-least-once delivery is assumed unless the selected platform proves otherwise; consumers must be idempotent.
Financial mutation completion events are interpreted using authoritative operation/resource IDs and versions.
Outbox/inbox or equivalent patterns are required where loss between durable state change and event publication would break evidence or job execution.
Dead-letter queues have ownership, alerting, replay tooling and security classification.
Replay must not repeat a financial effect; handlers use event_id/operation_id/idempotency keys.

15. Threat Model & Abuse Cases
[TABLE: 13 rows x 4 cols]
ID | Threat | Scenario | Primary mitigations
T-01 | Prompt injection / indirect injection | Retrieved content attempts to override system rules or call tools. | Instruction/data separation; tool allow-list; policy engine; no direct execution; injection tests.
T-02 | Cross-tenant data leakage | Prompt/search/cache key causes data from another tenant/entity. | Server context resolution; namespace filters; tenant-scoped cache keys; negative tests.
T-03 | Privilege escalation | User asks model to act as admin or change billing plane. | Server authorization; capability compilation; domain revalidation.
T-04 | Stale-preview execution | Resource changes after user previews effect. | Expiry, preview hash, resource version/ETag revalidation.
T-05 | Duplicate financial action | Network retry repeats invoice/refund/reconciliation. | Idempotency key, durable operation state, consumer deduplication.
T-06 | Tool argument manipulation | Model inserts hidden customer ID, amount or destination. | Typed schema, allow-list, entity ownership validation, preview display.
T-07 | Data exfiltration | User requests bulk restricted data through natural language. | Export scopes, result caps, DLP/classification policy, approval for bulk export.
T-08 | Model provider compromise/outage | Provider returns malicious/unavailable output. | Schema validation, provider isolation, fallback policy, deterministic action layer.
T-09 | Log/telemetry leakage | Sensitive prompt/service payload lands in logs. | Structured logging allow-list, redaction library, secret scanners.
T-10 | Webhook spoof/replay | External completion callback forged or replayed. | Signature verification/mTLS, timestamp/replay window, event deduplication.
T-11 | Denial of wallet | Automated expensive prompts/token abuse. | Rate limits, quotas, budgets, model tiers, max context/tool steps.
T-12 | Support misuse | Privileged staff accesses tenant information without purpose. | PAM/elevation, support session purpose, immutable audit, review alerts.
[END TABLE]
15.1 Security test obligation
Each threat above must have at least one automated or repeatable manual verification procedure, an owner, an expected safe result and evidence attached to the production security review. Architecture approval is not satisfied by a narrative threat model alone.

18. Network, Secrets & Cryptographic Boundaries
18.1 Network architecture
Public ingress terminates only at approved edge/gateway surfaces.
Application, data and administrative endpoints remain private where platform capability allows.
Egress is allow-listed for model providers, Billing services and necessary platform dependencies.
Database/vector/cache access is only from approved service identities/subnets/workloads.
Administrative access uses managed secure access paths; no permanent public database exposure.

19.2 Telemetry requirements
[TABLE: 7 rows x 2 cols]
Signal | Minimum dimensions / examples

21. Resilience, Timeouts & Graceful Degradation
[TABLE: 10 rows x 2 cols]
Failure | Required behavior
Model provider slow/unavailable | Use policy-approved fallback if safe; otherwise return controlled unavailable response. No financial state changes are inferred.
Retrieval service unavailable | Billing read/action APIs may continue where no KB evidence is required; policy/compliance answers fail safe.
Billing read API unavailable | Do not answer financial fact as current; optionally provide last-known timestamp only if explicitly labeled and product-approved.
Billing write timeout | Query durable operation/idempotency status. Do not blindly retry without contract.
Approval service unavailable | Keep action in safe waiting state; execution blocked.
Evidence DB unavailable | Protected mutation paths fail closed if required evidence cannot be durably recorded.
Cache unavailable | Degrade to durable stores with rate-limit/flood safeguards; no loss of authoritative state.
Event bus unavailable | Use transactional outbox/buffer; monitor backlog; do not drop required audit/action events.
Observability partial outage | Buffer best effort; security-critical telemetry failure policy may block privileged actions.
[END TABLE]
21.1 Resilience patterns
Per-dependency timeout budgets; no unbounded waits.
Exponential backoff with jitter for retryable idempotent operations.
Circuit breakers and bulkheads around provider/Billing dependencies.
Queue-based load leveling for long-running or bursty work.
Backpressure: reject/throttle before resource exhaustion.
Kill switches for model/provider, tool family, tenant capability, high-risk action class and knowledge namespace.
