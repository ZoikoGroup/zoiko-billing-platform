1. Executive Database Doctrine
[TABLE: 1 rows x 1 cols]
What this document controls This document defines the database and entity-relationship wireframe required to implement the Zoiko Billing Chatbot safely. It is not the final migration file, not a complete DDL package, and not a substitute for the authoritative Zoiko Billing financial schema.
[END TABLE]
Authoritative finance remains external: Invoices, payments, balances, allocations, credits, refunds, tax calculations and ledger state must be read from and committed through Zoiko Billing domain services only.
The chatbot records evidence: The chatbot database stores user utterances, assistant messages, model runs, retrieval provenance, proposed parameters, previews, confirmations, approvals, execution receipts and audit events.
All actions are governed: Consequential actions must flow through draft, preview, confirmation, approval when required, and execution. The database must make this progression auditable and impossible to skip.
No silent financial mutation: A generated response must never update financial state directly. Every mutating operation must have an immutable server-side action record and an authoritative execution result.
Two-plane isolation: Tenant billing data and Zoiko Billing's own SaaS commercial-account billing must remain in separate planes, with explicit database guards against context leakage.
Evidence over chat logs: Conversation logs are insufficient. Each material answer must connect to source documents, service responses, timestamps, actor identity, tenant/entity context and risk evaluation.
[TABLE: 6 rows x 3 cols]
Principle | Database implication | Production consequence
No shadow ledger | Only pointers to financial resources are stored; no duplicated invoice/payment ledgers. | Reconciliation, balances and ageing are calculated by Zoiko Billing services.
Context before data | Every session, message, action and retrieval carries tenant_id and legal_entity_id where applicable. | Cross-tenant data leakage becomes structurally preventable.
Preview before execution | Action preview records are immutable and expire. | Users cannot approve stale calculations.
Approvals are first-class | Approval requests and decisions are separate entities. | Maker-checker control is verifiable.
Grounding is recorded | Retrieval run, citations, document versions and freshness are stored. | Financial and policy answers can be challenged and reconstructed.
[END TABLE]
2. Scope and Non-Goals
[TABLE: 7 rows x 2 cols]
In scope | Out of scope / prohibited
Conversation sessions, messages and contextual metadata. | Replacing the Zoiko Billing invoice, payment, customer, tax or ledger databases.
Intent classification, risk class, policy evaluation and model-run metadata. | Allowing AI output to become an authoritative financial record.
Action drafts, previews, confirmations, approvals and execution receipts. | Committing financial changes without authoritative service validation.
Knowledge sources, versions, chunks, retrieval runs and citations. | Using Payroll or HR knowledge by default for a Billing chatbot.
Audit events, evidence packets, support access and operational controls. | Storing secrets, raw payment card data, full bank credentials or unnecessary PII.
Pointers to authoritative Zoiko Billing resources. | Duplicating invoice PDFs or payment ledgers unless required as immutable export/evidence references.
[END TABLE]
[TABLE: 1 rows x 1 cols]
Payroll / HR corpus control The engineer's source list included payroll policies, HR documentation and compliance documents. For Zoiko Billing, those materials must not enter the default chatbot knowledge namespace. They require explicit cross-product authorization, separate retrieval namespace, separate permissions and a visible source label.
[END TABLE]
3. Data Ownership Boundary
The chatbot database is an orchestration evidence store. Zoiko Billing financial services remain authoritative for financial state. The database must therefore be designed around references, not replication.
Figure 1 — Data boundary: chatbot evidence store, retrieval index and authoritative Zoiko Billing services
[TABLE: 9 rows x 4 cols]
Data class | System of record | Chatbot database role | Duplication rule
Customer profile | Zoiko Billing customer service | Pointer + displayed snapshot hash where needed. | No full duplicate except minimal display cache with TTL.
Invoice | Zoiko Billing invoice service | Pointer, preview payload summary, action evidence. | No duplicate invoice ledger.
Payment | Zoiko Billing payment service / PSP integrations | Pointer and operation receipt. | No PAN, CVV, full bank credentials or PSP secrets.
Balance / ageing | Zoiko Billing balance/ledger service | Query response evidence + timestamp. | No persisted calculated balance as truth.
Knowledge article | Approved Billing knowledge repository | Versioned metadata, chunk index and citations. | Permitted; source versions must be tracked.
Conversation | Chatbot database | Full system of record for chatbot interaction. | Permitted subject to retention rules.
Action approval | Chatbot/action control plane | Primary action-governance record. | Permitted and required.
Audit event | Evidence/audit store | Append-only activity evidence. | Permitted and required.
[END TABLE]
4. Storage Architecture Wireframe
[TABLE: 7 rows x 4 cols]
Storage component | Recommended technology class | Purpose | Notes
Relational database | PostgreSQL-compatible RDBMS | Conversations, actions, approvals, retrieval metadata, audit pointers and state transitions. | Primary ACID store for chatbot orchestration.
Vector index | Managed vector DB or pgvector-compatible index | Semantic retrieval over approved billing knowledge chunks. | No uncontrolled personal or financial payloads without classification.
Object storage | Encrypted object store | Evidence packets, export files, redacted transcript bundles and immutable snapshots. | Referenced by object_uri and content hash.
Cache | Redis-compatible ephemeral cache | Rate limiting, session acceleration, preview locks and idempotency hot keys. | Not system of record. TTL mandatory.
Event bus | Kafka/SNS/SQS/PubSub equivalent | Action completion, audit fan-out, webhook delivery and asynchronous jobs. | At-least-once delivery with idempotency.
Observability store | Logs/metrics/traces platform | Operational telemetry, SLIs and alerting. | Must redact secrets and restricted payloads.
[END TABLE]
Core relational schema: Use the relational store for all durable chatbot state and governance records.
Vector data isolation: Store chunk IDs and embedding references separately from financial action records to avoid accidental data blending.
Object storage discipline: Use object storage only for files and evidence packages; persist hashes, retention class and access policy in the database.
Cache discipline: Anything stored only in cache must be safe to lose.

6. Schema Design Standards
[TABLE: 13 rows x 2 cols]
Standard | Required rule
Identifier format | Use UUID/ULID-style immutable surrogate primary keys. Avoid natural keys as primary keys.
Tenant scope | All tenant-scoped tables must carry tenant_id; legal-entity-scoped tables must carry legal_entity_id.
Actor scope | All user-triggered records must carry actor_user_ref_id or system_actor_ref_id.
Timestamps | Use created_at, updated_at and, where relevant, expires_at, decided_at, executed_at and archived_at in UTC.
State fields | Use controlled enums for lifecycle states; prohibit free-text state.
Money fields | Use integer minor units plus ISO currency code for any temporary amount fields.
JSON fields | Allow JSONB for evidence snapshots only where schema version is stored and indexed keys are clear.
Hashing | Hash material evidence payloads and document versions using a modern content-hash strategy.
Soft delete | Use soft deletion only for non-evidence entities. Audit, approval and execution evidence must not be hard-deleted.
PII minimisation | Store the minimum data required for operation, audit and support. Prefer user_ref_id over raw personal attributes.
Schema version | Every complex JSON payload must carry schema_version.
Idempotency | Every mutating operation must support idempotency_key and request_fingerprint.
[END TABLE]
[TABLE: 1 rows x 1 cols]
Naming convention Use snake_case database names, singular table names where engineering convention permits, and consistent suffixes: _id for identifiers, _ref_id for external authoritative references, _at for timestamps, _hash for hashes, _json for structured payloads and _status for controlled state.
[END TABLE]

10. Indexing and Query Patterns
[TABLE: 9 rows x 3 cols]
Query pattern | Required indexes / design | Target behaviour
Load conversation history | conversation_id + created_at on conversation_message | Fast chronological render of recent messages.
Find pending approvals | tenant_context_id + request_status + expires_at on approval_request | Managers see pending decisions without scanning historical approvals.
Validate preview freshness | action_preview_id + preview_status + expires_at + resource_version_vector | Stale previews fail closed.
Trace an execution | correlation_id across action_execution, tool_invocation and audit_event | Single investigation path across systems.
Resource history | resource_type + resource_ref_id on financial_resource_pointer and service_response_snapshot | Investigate chatbot interactions involving a specific invoice/customer/payment.
Knowledge retrieval | knowledge_namespace_id + freshness_status + classification; vector index on embedding_ref/chunk text | Relevant, authorised and current retrieval.
Abuse/rate limits | user_ref_id/session_id + created_at event rollups | Detect excessive requests without persisting unsafe telemetry.
Support access audit | tenant_context_id + support_user_ref_id + started_at | Support access can be reviewed quickly.
[END TABLE]
Partitioning: Consider time-based partitioning for conversation_message, audit_event, model_run, tool_invocation and service_response_snapshot after volume thresholds are confirmed.
Hot paths: Optimize for current conversations, pending actions, pending approvals and recent financial resource investigations.
Cold paths: Archived conversations and evidence packets can move to lower-cost storage while keeping searchable metadata.
PII searches: Avoid direct indexes on sensitive text. Use reference IDs, hashes, classifications and approved support tooling.
11. Security, Privacy and Row-Level Governance
[TABLE: 11 rows x 2 cols]
Control | Database requirement
Tenant isolation | Every tenant-scoped query must filter by tenant_id through service context; row-level security should be enabled for high-risk tables where feasible.
Legal-entity isolation | Where tenant has multiple seller entities, legal_entity_id must be included for finance-related actions and answers.
Billing-plane isolation | billing_plane enum prevents tenant billing records and Zoiko commercial-account records from mixing.
Encryption | Encrypt data at rest; use envelope encryption for raw payload/object references and evidence packets.
Secret exclusion | Do not store API keys, PSP secrets, card data, CVV, bank passwords or raw OAuth tokens.
Data classification | Every knowledge source, chunk, attachment, snapshot and evidence packet carries classification.
Access logging | Support/admin reads must be logged through support_access_session and audit_event.
Prompt-injection resilience | Retrieved content cannot grant permissions, alter policy or issue hidden operational instructions.
Redaction | Raw payload retention requires classification, reason and retention class. Display text should be redacted where possible.
Export control | Evidence/export object URIs require signed, expiring access and audit events.
[END TABLE]

Action provenance: For actions, store proposed parameters, authoritative preview, confirmation, approval, idempotency key and execution receipt.

17. Migration and Versioning Standard
[TABLE: 9 rows x 2 cols]
Area | Requirement
Migration tool | Use engineering-approved migration tooling with forward-only production migrations and reversible lower-environment testing.
DDL review | All DDL affecting evidence, approvals or actions requires engineering, security and product review.
Zero-downtime | Additive migrations first; backfill; dual-read/write when needed; then remove old columns after compatibility window.
Enum changes | Controlled enum expansion only; no removal until historical data handling is approved.
JSON schema | Version every complex JSON payload and validate at service boundary.
Seed data | Prompt templates, policy codes, risk classes and namespaces require signed seed-data migrations.
Data backfill | Backfills must be idempotent, batched, observable and resumable.
Rollback | Rollback must not destroy audit evidence. Prefer feature rollback over destructive schema rollback.

19. Performance and Scale Targets
[TABLE: 14 rows x 3 cols]
